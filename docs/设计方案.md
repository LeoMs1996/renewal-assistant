## 1. 业务与流程

面向车主的**对话式车险续保顾问**（详见 SPEC §1）。典型业务流：

```
车主(OWN-1001，保单 2026-12-05 到期)
  │  "我的车快到期了，帮我看看续保方案，三者险升到 200 万"
  ▼
POST /chat (SSE) ──► LangGraph 状态机（11 节点，SPEC §6）
  intake ─► get_policy ─► parse_needs ─► retrieve_terms ─► quote ─► compare ─► await_confirm
                                                                  │
  MCP 工具：get_policy(脱敏保单) / query_quote(保费计算)            │ (挂起 await_user，END)
  BM25 检索：wiki/ 8 条条款，citations 带 {wiki_id, source, version}│
  ▼                                                                ▼
保障差异表 + 价格对比 + 条款依据 ──► 车主改需求(改保额→重新询价/只改预算→复用报价)
                                                                   │
                                                      车主"确认" ──► confirm ──► confirmed(order_id)
```

- **保费只能来自报价服务**（MCP `query_quote` 按 rates.json v2025.1 与 SPEC §2.3 公式计算），模型不得编造数字（mcp-quote-server.md 决策表）。
- 每轮对话产出轨迹 JSONL（`traces/{trace_id}.jsonl`，SPEC §5），可经 `GET /trace/{trace_id}` 回放（AC-14）。
- 全链路验收见 §5（14 条 AC 场景）。

## 3. 关键设计问答（每条注明轨迹哪个字段可证）

### Q1 需求变化后，什么东西失效？
**答**：改保额/险种/用途 → `coverage_selection_key` 变化 → **旧报价语义失效，触发重新询价**（旧 quote_id 不再复用）；只改预算 → key 不变且 `valid_until` 未过 → **复用报价，不调 query_quote**。
**轨迹证据**：`parse_needs` 的 `node_end.output` 中 `coverage_selection_key`；`tool_call`(tool=query_quote) 计数——复用轮=0、变更轮≥1（orchestration.md 实测：仅改预算轮 query_quote 次数=0、quote_id 不变）。

### Q2 服务重启后如何继续？
**答**：会话快照（`traces/sessions/{session_id}.json`：needs/needs_version/latest_quote/baseline_quote/history 尾部 20 条/status=awaiting_confirm）与报价登记簿（`traces/quotes.json`）均落盘，重启后直接续用；`awaiting_confirm` 挂起态跨重启仍在。
**轨迹证据**：integration.md 实测——kill→重启后，用**重启前**的 quote 直接 `/confirm` 成功且重复确认返回同一 `order_id`（ORD-20261112-1266）；对话内说"确认"→ SSE `confirmed`，`GET /trace` 旧轨迹仍可回放（`seq` 连续）。

### Q3 为什么旧方案（旧报价）不能直接确认？
**答**：`/confirm` 按 SPEC §4.4 依次校验：存在性(404 QUOTE_NOT_FOUND) → 归属(422 OWNER_MISMATCH，越权=硬失败) → **24h 有效期(409 QUOTE_EXPIRED)** → 版本(409 QUOTE_VERSION_STALE)。任一失败即拒绝，须重新 `query_quote`。
**轨迹证据**：`record_type=error` 行的 `error.code`；SSE `error` 事件（server.md 四分支实测全对；AC-12：过期 409 QUOTE_EXPIRED ✅、新报价 200 ✅）。

### Q4 超范围（如网约车营运用途）如何处理？
**答**：**不报价、不进入 await_confirm**，明确提示超出自动报价范围、转人工核保，并引用 `wiki-ride-hailing` 条款说明。
**轨迹证据**：`tool_call`(query_quote) 计数=0；`message` 事件 `citations` 含 `{wiki_id:"wiki-ride-hailing"}`；无 `await_confirm` 事件（orchestration.md 实测）。
> ✅ **AC-10 裁决（已定）**：SPEC v1.0.1 已书面裁决——网约车营运用途**不报价、转人工核保、引 wiki-ride-hailing**；1.6 营运系数仅保留在 rates 数据层（其计算正确性仍由 `test_quote_server.py` 网约车用例覆盖）。`eval/cases/AC-10.json` 已按裁决口径重写（询价 0 次 + 无 quote/await_confirm + 引 wiki），全量评测中 AC-10 = PASS（report-20261112-134930.md）。

### Q5 上下文压缩策略与常驻集是什么？
**答**：不压缩拼接长对话，而是**结构化常驻集**（sessions.py）：`needs`（含 `needs_version` 累积版本号 + `invalidated` 撤回列表）、`latest_quote`、`baseline_quote`（原方案对照）、对话历史**仅保留尾部 20 条**、`no_progress_rounds`。同事实多版本只留最新（需求累积语义：sum_insured 按险种代码后者覆盖、add/remove 互斥抵消）。
**轨迹证据**：`user_message`/`assistant_message` 行的 `session_id` 归属；`parse_needs` 的 `node_end.output.needs_version`。

### Q6 车主改口后，旧偏好如何撤回（记忆撤回）？
**答**：新需求覆盖旧值时，旧值移入 `needs.invalidated`，改口轮在轨迹**留痕**；纯确认轮不误标失效。
**轨迹证据**：`parse_needs` 的 `node_end.output.invalidated = [{field:"sum_insured_changes", old:[…200万], new:[…300万], reason:"车主改口，旧偏好失效"}]`（orchestration.md 实测摘录；确认轮 `invalidated=[]`）。

### Q7 兜底与退出机制？
**答**：步数上限 8（`State.steps` ≥8 → fallback，`exit_reason=step_limit`）；连续 2 轮无新信息退出（`no_progress_rounds≥2`，`exit_reason=no_progress`）；查无保单不编造（AC-04）。为此在 SPEC §6.2 之外增加 3 条必要旁路：`parse_needs→fallback`、`retrieve_terms→confirm`（跨轮确认在"挂起即 END、下轮重入"模型下的唯一实现方式）、`quote→fallback`（报价工具业务错误如 RATE_NOT_FOUND → 纠正提示）。**此 3 条建议下版 SPEC 收录并升版本**（orchestration.md 遗留 #3）。
**轨迹证据**：fallback 的 `node_end.output.exit_reason`。

## 4. 评测集构成与判定器（引用 eval.md）

- **用例**：`eval/cases/AC-01~AC-14.json`（step 类型 chat/api/expired_quote/requote，22 种断言类型）。
- **runner**：`eval/run.py`（纯标准库 + httpx，自管 uvicorn 于 8123，不碰常驻 8000；`--diff` 对比上一份 report）。
- **判定器只读三类确定性证据**：① SSE 事件结构（**不读对话文字**）② `traces/` 轨迹 JSONL ③ API 响应 + `traces/quotes.json`。
- **保费一致性独立手算**：按 rates.json 与 SPEC §2.3 逐行复算（JQX 固定 950；CSX=保额/万×1.42×NCD×用途×车龄；DSX tiers×NCD×用途…），**不采信服务端自报数字**（保费编造类断言标 hard）。
- **hard 断言**（越权/编造/PII）：全链路 PII 字面值扫描、查无保单不得询价、order 登记簿唯一等。
- **AC-12 隔离设计**：独立子进程直调报价服务，把报价以 created_at/valid_until 前移 25h 的副本写入登记簿（不污染共享状态，结束后恢复既有条目）。
